Git Flow ist ein Branching-Modell für Git, das von Vincent Driessen entwickelt wurde. Es definiert eine strikte Struktur für die Verwaltung von Branches in einem Git-Repository und eignet sich besonders für Projekte mit geplanten Releases.
## Die Hauptbranches

**Main Branch**: Enthält nur produktionsreife Code-Versionen. Jeder Commit hier sollte eine neue Release-Version darstellen.

**Develop Branch**: Der Integrationsbranch für Features. Hier wird der Code für das nächste Release gesammelt und getestet.

## Die unterstützenden Branches

**Feature Branches**: Werden vom develop-Branch abgezweigt und wieder zurück gemergt. Hier entwickelt man neue Features. Namenskonvention meist `feature/feature-name`.

**Release Branches**: Werden vom develop-Branch erstellt, wenn alle Features für ein Release fertig sind. Hier finden letzte Bugfixes und Vorbereitungen statt. Nach Fertigstellung wird sowohl in main als auch develop gemergt.

**Hotfix Branches**: Werden direkt vom main-Branch abgezweigt, um kritische Bugs in der Produktion schnell zu beheben. Werden sowohl in main als auch develop gemergt.

## Typischer Workflow

1. Neues Feature entwickeln: Branch von develop erstellen
2. Feature fertigstellen: Zurück in develop mergen
3. Release vorbereiten: Release-Branch von develop erstellen
4. Release fertigstellen: In main und develop mergen, Tag setzen
5. Hotfix bei Bedarf: Direkt vom main branchen und wieder zurück mergen

Git Flow bietet klare Regeln und Struktur, kann aber für kleinere Teams oder kontinuierliche Deployment-Strategien zu komplex sein. Moderne Alternativen wie GitHub Flow oder GitLab Flow sind oft einfacher zu handhaben.

---

GitHub Flow ist ein deutlich einfacheres Branching-Modell als Git Flow. Es wurde von GitHub entwickelt und eignet sich besonders für Teams, die kontinuierlich deployen.

## Die Grundprinzipien

GitHub Flow hat nur **einen Hauptbranch** (`main`), der immer deploybar sein sollte. Alle Entwicklung findet in Feature-Branches statt, die direkt von diesem Hauptbranch abzweigen.

## Der Workflow

**Branch erstellen**: Für jedes neue Feature, jeden Bugfix oder jede Änderung wird ein neuer Branch vom Hauptbranch erstellt. Der Name sollte beschreibend sein, z.B. `add-user-authentication` oder `fix-login-bug`.

**Commits hinzufügen**: Entwickle das Feature und committe regelmäßig. Die Commit-Messages sollten klar beschreiben, was geändert wurde.

**Pull Request öffnen**: Sobald du bereit bist für Feedback oder Hilfe brauchst, öffnest du einen Pull Request. Das kann schon früh im Entwicklungsprozess passieren - auch für Work-in-Progress.

**Code Review**: Andere Teammitglieder reviewen deinen Code, geben Feedback und diskutieren Änderungen direkt im Pull Request.

**Mergen**: Nach erfolgreichem Review wird der Pull Request in den Hauptbranch gemergt. Der Feature-Branch wird danach gelöscht.

**Deployment**: Da der Hauptbranch immer deploybar sein soll, kann nach dem Merge direkt deployed werden.

## Vorteile

GitHub Flow ist sehr einfach zu verstehen und umzusetzen. Es passt perfekt zu modernen Entwicklungspraktiken wie Continuous Integration/Deployment und fördert häufige, kleine Releases. Die Pull Request-basierte Entwicklung sorgt für bessere Code-Qualität durch Reviews.

Das Modell funktioniert besonders gut für Web-Anwendungen und Services, wo schnelle Iterationen wichtig sind.
