Hier ist eine detaillierte Schritt-für-Schritt-Beschreibung eines kompletten GitHub Flow Ablaufs:
## Ausgangssituation

Du arbeitest an einer Web-Anwendung. Der `main`-Branch enthält die aktuelle Produktionsversion. Du sollst ein neues Feature implementieren: eine Benutzer-Registrierung.

## Schritt 1: Aktuellen Stand holen

```bash
git checkout main
git pull origin main
```

Stelle sicher, dass dein lokaler `main`-Branch auf dem neuesten Stand ist.

## Schritt 2: Feature-Branch erstellen

```bash
git checkout -b add-user-registration
```

Erstelle einen neuen Branch mit einem beschreibenden Namen. Der Branch wird automatisch vom aktuellen `main`-Branch abgezweigt.

## Schritt 3: Feature entwickeln

Jetzt implementierst du das Feature in mehreren Commits:

```bash
# Erste Änderungen
git add registration-form.html
git commit -m "Add basic registration form HTML structure"

# Weitere Entwicklung
git add styles/registration.css
git commit -m "Add styling for registration form"

git add js/registration.js
git commit -m "Add client-side form validation"

git add backend/user-controller.js
git commit -m "Implement user registration endpoint"
```

## Schritt 4: Branch auf GitHub pushen

```bash
git push origin add-user-registration
```

Damit wird dein Feature-Branch auf GitHub verfügbar und andere können deine Arbeit sehen.

## Schritt 5: Pull Request erstellen

Auf GitHub gehst du zu deinem Repository und klickst auf "Compare & pull request". Du füllst aus:

**Titel**: "Add user registration feature"

**Beschreibung**:

```
## Was wurde implementiert
- Registrierungsformular mit E-Mail und Passwort
- Client-seitige Validierung
- Backend-Endpoint für Benutzer-Erstellung
- Passwort-Hashing mit bcrypt

## Tests
- [ ] Formular validiert E-Mail-Format
- [ ] Passwort-Mindestlänge wird geprüft
- [ ] Benutzer wird in Datenbank gespeichert
- [ ] Duplicate E-Mails werden abgelehnt

## Screenshots
[Hier würdest du Screenshots einfügen]

Fixes #123
```

## Schritt 6: Code Review Prozess

Deine Kollegen reviewen den Code:

**Sarah kommentiert**: "Die Passwort-Validierung sollte auch Sonderzeichen prüfen"

Du antwortest und machst die Änderung:

```bash
git add js/registration.js
git commit -m "Add special character validation for passwords"
git push origin add-user-registration
```

**Tom fragt**: "Haben wir Tests für den Backend-Endpoint?"

Du ergänzt Tests:

```bash
git add tests/user-registration.test.js
git commit -m "Add unit tests for user registration endpoint"
git push origin add-user-registration
```

## Schritt 7: Continuous Integration

GitHub Actions (oder ein anderes CI-System) läuft automatisch:

- Code-Linting
- Unit Tests
- Integration Tests
- Security Scans

Alle Checks sind grün ✅

## Schritt 8: Final Review und Approval

Nach mehreren Review-Runden geben deine Kollegen ihr "Approved" ✅. Der Pull Request ist bereit zum Mergen.

## Schritt 9: Mergen

Du (oder ein Maintainer) klickst auf "Merge pull request" auf GitHub. Du wählst "Squash and merge" um die Commit-Historie sauber zu halten.

Der Merge-Commit bekommt die Message:

```
Add user registration feature (#124)

* Add basic registration form HTML structure
* Add styling for registration form  
* Add client-side form validation
* Implement user registration endpoint
* Add special character validation for passwords
* Add unit tests for user registration endpoint
```

## Schritt 10: Branch aufräumen

```bash
git checkout main
git pull origin main
git branch -d add-user-registration
git push origin --delete add-user-registration
```

Der Feature-Branch wird lokal und remote gelöscht, da er nicht mehr benötigt wird.

## Schritt 11: Deployment

Da der `main`-Branch immer deploybar sein sollte, wird automatisch (via CI/CD Pipeline) oder manuell deployed. Das neue Feature ist jetzt live!

## Besonderheiten während des Prozesses

**Bei Konflikten**: Wenn sich der `main`-Branch während deiner Entwicklung geändert hat:

```bash
git checkout main
git pull origin main
git checkout add-user-registration
git rebase main
# Konflikte lösen falls nötig
git push origin add-user-registration --force-with-lease
```

**Draft Pull Requests**: Du kannst auch früh einen "Draft" Pull Request erstellen, um Feedback zu bekommen, bevor das Feature fertig ist.

**Automatische Checks**: Moderne Setups blockieren das Mergen, wenn Tests fehlschlagen oder Code-Qualitäts-Standards nicht erfüllt sind.

Dieser Ablauf wiederholt sich für jedes Feature, jeden Bugfix und jede Änderung. Die Einfachheit macht GitHub Flow sehr vorhersagbar und effizient für Teams.

Hier ist der gleiche User-Registration-Feature-Prozess im klassischen Git Flow:

## Ausgangssituation

Du hast zwei permanente Branches:

- `main`: Produktionsversion (v2.1.0)
- `develop`: Integrationsbranch mit Features für das nächste Release

## Schritt 1: Aktuellen Develop-Stand holen

```bash
git checkout develop
git pull origin develop
```

**Wichtiger Unterschied**: Du startest vom `develop`-Branch, nicht vom `main`.

## Schritt 2: Feature-Branch erstellen

```bash
git flow feature start user-registration
# Oder manuell:
git checkout -b feature/user-registration develop
```

Der Branch wird mit `feature/` prefixed und vom `develop`-Branch abgezweigt.

## Schritt 3: Feature entwickeln

```bash
git add registration-form.html
git commit -m "Add basic registration form HTML structure"

git add styles/registration.css  
git commit -m "Add styling for registration form"

git add js/registration.js
git commit -m "Add client-side form validation"

git add backend/user-controller.js
git commit -m "Implement user registration endpoint"
```

Die Entwicklung läuft gleich ab wie bei GitHub Flow.

## Schritt 4: Feature fertigstellen

```bash
git flow feature finish user-registration
```

Das passiert automatisch:

1. Wechsel zu `develop`-Branch
2. Merge des Feature-Branches in `develop`
3. Löschen des Feature-Branches
4. Zurück zum `develop`-Branch

Manuell wäre das:

```bash
git checkout develop
git merge --no-ff feature/user-registration
git branch -d feature/user-registration
```

## Schritt 5: Weitere Features sammeln

Das User-Registration-Feature ist jetzt im `develop`-Branch. Andere Entwickler arbeiten parallel an anderen Features:

```bash
# Kollege entwickelt Passwort-Reset
git flow feature start password-reset

# Andere Kollegin arbeitet an User-Profile
git flow feature start user-profile
```

Alle Features werden nacheinander in `develop` integriert.

## Schritt 6: Release vorbereiten

Wenn genug Features für Version 2.2.0 gesammelt sind:

```bash
git flow release start 2.2.0
# Oder manuell:
git checkout -b release/2.2.0 develop
```

## Schritt 7: Release-Vorbereitungen

Im `release/2.2.0`-Branch werden nur noch finale Anpassungen gemacht:

```bash
# Version in package.json aktualisieren
git add package.json
git commit -m "Bump version to 2.2.0"

# Kleinere Bugfixes
git add bugfix.js
git commit -m "Fix minor validation bug found in testing"

# Changelog aktualisieren
git add CHANGELOG.md
git commit -m "Update changelog for v2.2.0"
```

## Schritt 8: Release finalisieren

```bash
git flow release finish 2.2.0
```

Das passiert automatisch:

1. Merge des Release-Branches in `main`
2. Tag `v2.2.0` wird auf `main` erstellt
3. Merge des Release-Branches zurück in `develop` (für Bugfixes)
4. Löschen des Release-Branches

## Schritt 9: Deployment

```bash
git checkout main
git pull origin main
# Deploy Version 2.2.0 zur Produktion
```

## Schritt 10: Hotfix-Szenario (optional)

Angenommen, es gibt einen kritischen Bug in der Registrierung:

```bash
git flow hotfix start registration-security-fix
# Oder manuell:
git checkout -b hotfix/registration-security-fix main
```

Bugfix implementieren:

```bash
git add security-fix.js
git commit -m "Fix SQL injection vulnerability in registration"
```

Hotfix fertigstellen:

```bash
git flow hotfix finish registration-security-fix
```

Das passiert:

1. Merge in `main` → neue Version 2.2.1
2. Merge in `develop` → Fix ist auch im nächsten Release
3. Tag `v2.2.1` wird erstellt
4. Hotfix-Branch wird gelöscht

## Vergleich der beiden Workflows

|Aspekt|GitHub Flow|Git Flow|
|---|---|---|
|**Start-Branch**|`main`|`develop`|
|**Branch-Namen**|`add-user-registration`|`feature/user-registration`|
|**Merge-Ziel**|Direkt in `main`|Erst `develop`, später über Release in `main`|
|**Deployment**|Nach jedem Merge möglich|Nur bei Release-Branches|
|**Code Review**|Über Pull Request|Optional, meist lokal|
|**Komplexität**|Sehr einfach|Komplexer, mehr Branches|
|**Release-Planung**|Continuous Delivery|Geplante Releases|

## Zeitliche Unterschiede

**GitHub Flow**: Das User-Registration-Feature wäre nach 2-3 Tagen in Produktion.

**Git Flow**: Das Feature wartet im `develop`-Branch, bis genug andere Features für Release 2.2.0 fertig sind. Das könnte 2-4 Wochen dauern. Dann erst kommt es über den Release-Prozess in die Produktion.

Git Flow eignet sich besser für traditionelle Software mit geplanten Releases (z.B. Desktop-Software, Mobile Apps), während GitHub Flow ideal für Web-Services mit kontinuierlichem Deployment ist.
