Ein Programm tut immer genau das, was im Code steht. Ein Bug entsteht dort, wo das nicht mit dem übereinstimmt, was man *glaubt*, dass der Code tut. Jeder Bug hat deshalb zwei Seiten: einen technischen Fehler im Code und einen Fehler in der eigenen Vorstellung davon, was gerade passiert.

Daraus folgt die übliche Reihenfolge beim Debuggen: erst herausfinden, was das Programm wirklich tut – mit Ausgaben, dem Debugger oder dem Variablenbereich –, und erst dann etwas ändern. Wer sofort repariert, ändert den Code auf Grundlage genau des Bildes, das falsch ist.

Für Anfänger reicht diese Regel allein nicht. Sie können oft nicht einschätzen, welcher der vorher scheinbar funktionierenden Schritte das Problem verursacht, und wissen nicht, wo sie nachfragen können. Aufgaben in passender Schwierigkeit und eine Gruppe oder ein Forum gehören deshalb ebenso zum Debuggen-Lernen wie die Werkzeuge.
