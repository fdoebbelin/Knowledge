## 1. WARUM SCRUM FÜR EIN FIRMENJUBILÄUM?

### Vorteile der agilen Event-Planung:

- **Flexibilität:** Schnelle Anpassung bei Änderungswünschen
- **Transparenz:** Regelmäßige Reviews mit Stakeholdern
- **Risikominimierung:** Frühe Erkennung von Problemen
- **Stakeholder-Einbindung:** Kontinuierliches Feedback
- **Iterative Verbesserung:** Schrittweise Optimierung des Events

### Event-Management meets Scrum:

- **Product:** Das perfekte Firmenjubiläum
- **Sprints:** 2-Wochen-Zyklen für verschiedene Event-Bereiche
- **User Stories:** Anforderungen aus Sicht aller Teilnehmer
- **Daily Scrums:** Kurze Abstimmungen im Planungsteam

## 4. SPRINT-PLANUNG IN PROJEQTOR

### Sprint-Struktur (6 Sprints à 2 Wochen = 12 Wochen)

#### **Sprint 1: Foundation (Wochen 1-2)**

**Sprint Goal:** Location sichern und erste Planungsgrundlagen schaffen

**Sprint Backlog:**

```
- User Story 1.1: Location finden und buchen (8 SP)
- User Story 3.1: Save-the-Date versenden (5 SP)
- Technical Task: Budget finalisieren (3 SP)
- Technical Task: Dienstleister-Longlist erstellen (2 SP)

Sprint Capacity: 18 Story Points
Team Velocity: Erste Schätzung
```

#### **Sprint 2: Infrastructure (Wochen 3-4)**

**Sprint Goal:** Technische und kulinarische Grundlagen legen

**Sprint Backlog:**

```
- User Story 1.2: AV-Technik beauftragen (5 SP)
- User Story 2.2: Programm-Konzept entwickeln (8 SP)
- User Story 4.1: Catering auswählen und buchen (8 SP)
- Technical Task: Sicherheitskonzept erstellen (2 SP)

Sprint Capacity: 23 Story Points
```

#### **Sprint 3: Content & Experience (Wochen 5-6)**

**Sprint Goal:** Programm finalisieren und Gästeerlebnis optimieren

**Sprint Backlog:**

```
- User Story 2.1: Programm final planen (13 SP)
- User Story 5.1: Logistik-Konzept erstellen (13 SP)
- Technical Task: Moderator/Entertainment buchen (5 SP)

Sprint Capacity: 31 Story Points
```

#### **Sprint 4: Communication (Wochen 7-8)**

**Sprint Goal:** Marketing aktivieren und Teilnehmer mobilisieren

**Sprint Backlog:**

```
- User Story 3.2: Mediale Begleitung vorbereiten (8 SP)
- Technical Task: Offizielle Einladungen versenden (3 SP)
- Technical Task: Website/Landing Page erstellen (5 SP)
- Technical Task: RSVP-System einrichten (3 SP)

Sprint Capacity: 19 Story Points
```

#### **Sprint 5: Final Preparations (Wochen 9-10)**

**Sprint Goal:** Letzte Vorbereitungen und Tests durchführen

**Sprint Backlog:**

```
- Technical Task: Generalprobe/Walk-through (8 SP)

- Technical Task: Notfallpläne ausarbeiten (3 SP)

#### **Sprint 6: Event & Wrap-up (Wochen 11-12)**

**Sprint Goal:** Event durchführen und nachbereiten

**Sprint Backlog:**

```
- Technical Task: Event-Durchführung (21 SP)

## 6. SCRUM EVENTS IN PROJEQTOR

### 6.1 Sprint Planning Meeting

```
Meeting-Typ: Sprint Planning
Dauer: 4 Stunden (bei 2-Wochen-Sprint)
Teilnehmer: Gesamtes Scrum Team
Recurring: Alle 2 Wochen

Agenda:
1. Sprint Goal definieren (30 min)
2. Product Backlog Review (60 min)
3. Sprint Backlog erstellen (120 min)
4. Capacity Planning (30 min)

Ergebnis: Sprint Backlog in ProjeQtor Activities
```

### 6.2 Daily Scrum

```
Meeting-Typ: Daily Scrum
Dauer: 15 Minuten
Teilnehmer: Development Team + Scrum Master
Recurring: Täglich (Mo-Fr)
Zeit: 9:00 Uhr

Standardfragen:
1. Was habe ich gestern erreicht?
2. Was plane ich heute?
3. Welche Hindernisse gibt es?

Dokumentation: Kurze Notizen im Meeting-Protokoll
```

### 6.3 Sprint Review
```
Meeting-Typ: Sprint Review
Dauer: 2 Stunden
Teilnehmer: Scrum Team + Stakeholder
Recurring: Ende jedes Sprints

Format:
1. Sprint Goal erreicht? (15 min)
2. Demo der Ergebnisse (60 min)
3. Stakeholder Feedback (30 min)
4. Product Backlog Update (15 min)

Output: Aktualisiertes Product Backlog
```

### 6.4 Sprint Retrospective
```
Meeting-Typ: Sprint Retrospective
Dauer: 1,5 Stunden
Teilnehmer: Scrum Team (intern)
Recurring: Nach jedem Sprint Review

Methode: Start-Stop-Continue
1. Was sollen wir anfangen? (30 min)
2. Was sollen wir aufhören? (30 min)
3. Was sollen wir weiter machen? (30 min)

Actions: Verbesserungsmaßnahmen als Activities in ProjeQtor
```

## 12. VORTEILE SCRUM VS. KLASSISCHES PM

### Vergleich für Event-Management:

| Aspekt          | Klassisches PM             | Scrum                                 |
| --------------- | -------------------------- | ------------------------------------- |
| **Planung**     | Detailplan zu Beginn       | Iterative Verfeinerung                |
| **Änderungen**  | Change Request Prozess     | Flexible Anpassung im nächsten Sprint |
| **Stakeholder** | Regelmäßige Statusberichte | Aktive Einbindung in Reviews          |
| **Risiken**     | Risikoregister             | Risiken als User Stories behandelt    |
| **Qualität**    | Qualitätssicherung am Ende | Kontinuierliche Qualitätskontrolle    |
| **Team**        | Funktionale Silos          | Cross-funktionales Team               |
| **Feedback**    | Feedback bei Meilensteinen | Feedback alle 2 Wochen                |

### Besondere Scrum-Vorteile für Events:

1. **Kreativitäts-Zyklen:** Alle 2 Wochen neue Ideen entwickeln
2. **Stakeholder-Buy-in:** Frühe und häufige Einbindung
3. **Lieferanten-Integration:** Externe Partner in Sprint Reviews
4. **Qualitätsoptimierung:** Kontinuierliche Verbesserung
5. **Transparenz:** Jederzeit aktueller Status sichtbar

## 13. LESSONS LEARNED: SCRUM FÜR EVENTS

### Was funktioniert besonders gut:

```
✅ Sprint Reviews für Stakeholder-Alignment
✅ Daily Scrums für schnelle Koordination
✅ Kanban Board für Transparenz
✅ User Stories für klare Anforderungen
✅ Retrospektiven für kontinuierliche Verbesserung
```

### Anpassungen für Event-Management:

```
🔄 Sprint-Länge an Event-Deadline anpassen
🔄 DoD für jede Story-Kategorie spezifisch definieren
🔄 Planning Poker für komplexe Eventplanung kalibrieren
🔄 Externe Dienstleister in Scrum Events integrieren
🔄 Wetterabhängige Stories besonders berücksichtigen
```

### Anti-Patterns vermeiden:

```
❌ Zu viele User Stories ohne klaren Sprint-Focus
❌ Stakeholder-Overload in Sprint Reviews
❌ Sprint Goals zu vage formuliert
❌ Daily Scrums als Status-Meetings missbrauchen
❌ Planning Poker ohne Event-spezifische Kalibrierung
```
